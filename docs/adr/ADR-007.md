# ADR-007 — Single-Host, Private-by-Default MVP Release

**Status:** Accepted  
**Date:** 2026-10-19  
**Target:** Nexus Research `v0.1.0`  
**Related:** `docs/specs/phase-7-release/spec.md`, ADR-004/005/006

## Context

Nexus Research has a working FastAPI + LangGraph research engine, Next.js SSE UI, PostgreSQL domain history and checkpoints, Qdrant evidence, optional OTel and an offline-first evaluation suite. The development Compose file currently provisions data services, not API/Web. Release needs reproducible packaging and an honest operational/security boundary without turning a 14-day single-operator MVP into a SaaS platform.

## D1 — Release MVP first; Alpha is a separate milestone

**Decision:** tag the existing feature set as `v0.1.0` after packaging, smoke verification and documentation. Authentication, `user_id` tenancy, admin evaluation dashboard, UI redesign and landing are explicitly deferred to Alpha `v0.2.0`.

**Why:** separate technical reproducibility from product adoption and avoid scope creep.

**Alternative:** ship all Alpha features in MVP (rejected: changes authorization model and increases release risk).

## D2 — Docker Compose on one host, not distributed infrastructure

**Decision:** package API and Web as containers, alongside PostgreSQL and Qdrant on a private Compose network with named volumes. Optional Jaeger remains opt-in. No Kubernetes, queue, worker or HA promises.

**Why:** smallest repeatable deployment consistent with current runtime and project learning objectives.

**Trade-off:** single-host failure domain and maintenance windows; not production-grade availability.

## D3 — Keep development Compose stable; add explicit release Compose

**Decision:** prefer `compose.release.yml` as a standalone full-stack configuration, invoked with `docker compose -f compose.release.yml ...`. Keep existing root `docker-compose.yml` for current local infra commands. Do not unintentionally merge Compose files; document exact `-f` commands.

**Why:** avoid breaking established developer workflows while keeping release configuration auditable.

**Alternative:** replace root Compose entirely (rejected unless proven migration is simpler and all docs/tests updated).

**Implementation caveat:** inspect current Docker/Compose configuration and adjust paths, network names and secrets before coding. This ADR specifies intent, not existing files.

## D4 — Private-by-default exposure, no public anonymous demo

**Decision:** only Web publishes a host port, bound to `127.0.0.1`; API/PostgreSQL/Qdrant are internal. Remote demo requires VPN/SSH tunnel or an independently enforced authentication gate. Do not publicly expose billable research endpoints without auth and rate limits.

**Why:** `research_id` scopes evidence but does not authorize a user; the current history API has no user ownership.

**Alternatives:** public anonymous deployment (rejected); implement full auth in Phase 7 (deferred to Alpha).

**Trade-off:** harder to share a public demo; acceptable for developer MVP.

## D5 — Immutable-ish image builds and non-root runtime

**Decision:** use Python 3.14 and Node 24, install from committed `uv.lock` and `package-lock.json`, build production images without source bind mounts, use non-root runtime, exclude secrets with `.dockerignore` and minimize runtime dependencies. Pin image versions; digest pins preferred if operationally practical.

**Why:** reproducible dependency graph and reduced attack surface.

**Trade-off:** build maintenance, possible native package compatibility; do not claim bitwise reproducibility without verification.

## D6 — One-shot schema init, separate ownership

**Decision:** an explicit init step runs Alembic domain migrations and the existing LangGraph checkpoint setup, then exits. API/Web depend on successful initialization and healthy data services. Both commands must be tested for idempotency.

**Why:** checkpoint tables are not Alembic-managed; startup must not race schema creation.

**Alternatives:** run migrations on every API process startup (rejected: race and hidden lifecycle); manual undocumented shell commands (rejected).

**Trade-off:** extra Compose service and startup sequencing; failed init blocks release until repaired.

## D7 — Preserve request-scoped research and SSE contracts

**Decision:** maintain existing synchronous/request-scoped research, streaming proxy, heartbeat, cancellation, graph budget and domain history behavior. No background resume, no API/SSE schema changes unless a proven release-blocking bug requires a separately reviewed fix.

**Why:** Phase 7 packages and validates, not redesigns orchestration.

**Trade-off:** process restart can interrupt in-flight work; stale `running` remains possible.

## D8 — Offline-first CI; paid demo manually verified

**Decision:** retain Ruff, mypy, pytest, Web checks, offline evaluation and frozen baseline. Add container image build and packaged smoke checks. Live OpenAI/Tavily research is a documented, explicit manual release gate, never a PR requirement.

**Why:** reproducible CI without secrets/costs, with actual end-to-end demonstration before release claim.

**Trade-off:** offline CI cannot establish live provider availability, grounding accuracy or production retrieval relevance.

## D9 — No new observability or persistence platform

**Decision:** reuse existing JSON logs, OTel, run history, evaluation CLI and JSON artifacts. Tracing disabled by default; Jaeger optional. No new metrics DB or evaluation dashboard in MVP.

**Why:** avoids operational overhead and protects Phase 6 separation of deterministic and probabilistic measurements.

## D10 — Explicit release and rollback contract

**Decision:** release uses reviewed commit, changelog, tagged `v0.1.0`, documented image/build source and smoke evidence. Do not auto-tag or auto-push. Rollback of app images is possible only when schema remains compatible; restoring database/Qdrant volumes requires separately tested backups. No blanket rollback guarantee.

**Why:** reproducibility includes honest recovery limitations.

## Consequences

**Positive:** portable developer demo, repeatable deployment, auditable release boundary, minimal operational complexity, safe path toward Alpha.

**Negative:** not a publicly accessible multi-user SaaS; no HA, background resume, hosted dashboard or durable PDF originals; operator must configure provider credentials and backups.

## Validation

Accept this ADR when the Phase 7 specification's AC-01 through AC-11 have documented evidence and no known release-blocking regression remains. Implementation details (base image digest, exact init command, Compose health check) must be confirmed against the branch during Step 1 rather than guessed.
