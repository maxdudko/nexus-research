# ADR-004 — Bounded LangGraph Orchestration with PostgreSQL Checkpoints

**Status:** Proposed for approval  
**Date:** 2026-10-16  
**Extends:** ADR-001, ADR-002, ADR-003

## Context

Phase 2 exposes structured planning and bounded Tavily discovery; Phase 3 exposes independently testable ingestion and accepted-version retrieval. Phase 4 must combine these services into an end-to-end research workflow without sacrificing bounded execution, source provenance or future Phase 5 compatibility.

## Decision 1 — LangGraph StateGraph as the orchestration layer

Use `StateGraph` with typed state, explicit nodes and conditional edges for planning, discovery, ingestion, retrieval, coverage evaluation and synthesis. Graph nodes call existing services rather than implementing their internals.

**Alternatives:** hand-written Python orchestration; unrestricted ReAct agent; LangChain chains.

**Rationale:** Graph state, conditional transitions and checkpointing are useful for research loops and later progress reporting. **Cost:** additional framework complexity and state serialization requirements.

## Decision 2 — Request-scoped asynchronous execution

Use `await graph.ainvoke(...)` inside `POST /api/v1/research/run` with a hard overall deadline and explicit budgets. This is asynchronous I/O but the HTTP request waits for completion. No queue, detached task, worker or fire-and-forget execution.

**Alternatives:** Celery/Redis, FastAPI BackgroundTasks, separate workflow service.

**Rationale:** smallest viable end-to-end API and straightforward testability. **Cost:** long-lived requests, proxy timeout constraints, no execution after client disconnect/process crash. A checkpoint is not a worker.

## Decision 3 — PostgreSQL AsyncPostgresSaver for checkpoints

Use a compatible LangGraph PostgreSQL async checkpointer with explicit setup and lifecycle, backed by existing PostgreSQL infrastructure. `InMemorySaver` is for isolated tests. Verify exact APIs and pool ownership against locked versions before coding.

**Alternatives:** memory only; Redis checkpointing; custom state persistence.

**Rationale:** state survives API restarts and supports later resume design. **Cost:** checkpoint schema, lifecycle management and retention; no automatic recovery/exactly-once guarantees.

## Decision 4 — Separate run identity from evidence scope

Generate a fresh `run_id`/LangGraph `thread_id` for each invocation. Use a distinct `research_id` for evidence scope, optionally supplied for previously indexed PDFs. Do not use a user-supplied `thread_id`. Reuse of research scope does not grant access rights: authentication is out of scope.

**Alternatives:** equate thread ID with research ID; one Qdrant collection per run.

**Rationale:** supports future reruns without overwriting previous execution checkpoints. **Cost:** two IDs and a future domain-level run history projection.

## Decision 5 — Global deterministic budgets govern nested agents

A deterministic Python policy limits iterations, cumulative searches, LLM calls, pages, selected evidence and deadline. Model coverage assessment informs routing but cannot override limits. `Discovery` already performs up to three searches and four LLM calls internally; enforce remaining budget before each invocation or minimally extend its API to accept per-call caps. Record actual calls; distinguish SDK retries from logical calls.

**Alternatives:** rely only on LangGraph recursion_limit; trust LLM stop decision.

**Rationale:** predictable cost and termination. **Cost:** occasional partial reports despite remaining research opportunities.

## Decision 6 — Accepted evidence only; no source-content checkpointing

Use `IngestionService` and `RetrievalService` unchanged in role. Persist only compact metadata/selected evidence IDs in state; load accepted-version passages as needed. All external content is untrusted. Existing SSRF and research-scoped filters remain mandatory.

**Alternatives:** checkpoint full web/PDF text or embeddings; reimplement RAG as graph nodes.

**Rationale:** low checkpoint overhead and clear ownership. **Cost:** resumption may require re-querying Qdrant; raw PDFs are not durably stored.

## Decision 7 — Grounded structured reports with verified references

Synthesis receives bounded retrieved passages labeled with server-assigned IDs. Validate output schema and that cited IDs belong to selected evidence. Resolve URLs/pages from retrieval metadata only. Report partial coverage and uncertainty. Do not claim citation existence proves factual support; Phase 6 will evaluate entailment.

**Alternatives:** free-form Markdown answer with arbitrary links; separate fact-checking agent now.

**Rationale:** stable API and auditable provenance. **Cost:** more validation, imperfect factual grounding remains possible.

## Decision 8 — Thin API, checkpoint ≠ research history

Add `/api/v1/research/run` without changing `/plan`, `/discover` or evidence endpoints. The final report is returned and checkpointed; checkpointer tables are internal, not a supported listing/search API. Defer dedicated `research_runs` metadata table until Phase 5 unless a concrete need emerges.

**Alternatives:** expose checkpointer tables as history; build full research-run persistence now.

**Rationale:** minimize Phase 4 scope while leaving a clean upgrade path.

## Decision 9 — Deterministic partial/failure policy

When coverage is insufficient or budgets expire, synthesize only from available evidence and mark partial/insufficient. Infrastructure/provider failures are classified separately and never reported as successful research. Checkpoint replay is at-least-once in effect for external actions; ingestion must remain idempotent, and repeated discovery may incur cost.

## Consequences and revisit triggers

**Positive:** end-to-end workflow, durable checkpoints, explicit bounds, preserved service boundaries, Phase 5-ready graph progress events.

**Negative:** long HTTP requests, two persistence concerns, provider cost accounting complexity, checkpoint migration/retention burden, no automatic background continuation.

Revisit when UI requires reliable long-running jobs/SSE across disconnects, when reports must be queryable by history, when authenticated multi-user access is introduced, or when checkpoint recovery needs automatic scheduling.

## Compatibility

- Python 3.14 and uv lock must be respected; verify `langgraph` and `langgraph-checkpoint-postgres` versions.
- Preserve `create_app(settings)`, lifespan DB engine/session factory, existing router and sanitized errors.
- No changes to Source/Qdrant acceptance rules or Phase 2 API contracts.
- Optional API credentials at startup; missing keys fail only dependent operations.
