# ADR-002 — OpenAI, Tavily and Bounded Tool Calling

**Status:** Proposed — awaiting approval  
**Date:** 2026-10-13  
**Decision owners:** Nexus Research project  
**Supersedes:** None; extends ADR-001

## Context

Phase 1 delivered an async FastAPI foundation with Python 3.14, uv, Pydantic Settings, SQLAlchemy and test/CI infrastructure. Phase 2 must teach practical LLM integration and tool calling while keeping the later LangGraph/RAG architecture flexible. The owner chose **OpenAI**, **Tavily** and **one configurable model**.

## Decisions

### D1 — OpenAI only, one configurable chat model

Use `ChatOpenAI` from `langchain-openai`, configured through `NEXUS_OPENAI_MODEL` and `NEXUS_OPENAI_API_KEY`. Instantiate lazily when an AI endpoint needs it. A single model handles planning and discovery.

**Alternatives:** Native OpenAI SDK only; multi-provider abstraction; separate planner/discovery models.

**Rationale:** Learn LangChain model abstractions that carry forward into LangGraph while retaining a simple configuration surface. Native SDK examples may be used for learning, but not duplicated in the production path.

**Consequences:** Model capabilities must be checked for both structured output and tool calling. Model names and supported parameters may change; do not hard-code unsupported `temperature` or reasoning options. The model is configurable, not auto-selected by application logic.

### D2 — Structured output via Pydantic and LangChain

Use `with_structured_output(..., method="json_schema")` for the planner. Keep provider-facing schema minimal and perform separate application-level bounds checking. Validate output even if the provider reports schema compliance.

**Alternatives:** Parse free-form JSON from a prompt; use tool-calling-as-output; manually invoke OpenAI Responses API.

**Rationale:** Clear typed contract, simpler tests and fewer parsing ambiguities.

**Trade-off:** Strict provider JSON Schema supports a narrower subset of Pydantic constraints. A fallback method is acceptable only if compatibility testing demonstrates it is needed and the change is documented.

### D3 — Tavily Search API through official async SDK

Use the official `AsyncTavilyClient` and its `search()` operation, with a narrow `web_search(query)` application tool. Normalize output into our own `SearchResult` schema.

**Alternatives:** Exa, OpenAI built-in web search, direct HTTPX calls, Tavily Research API.

**Rationale:** The search call remains an observable backend action; model-issued tool calls and tool responses can be studied and tested. Tavily Research API is intentionally excluded because it would perform much of the research orchestration externally.

**Consequences:** Another API key, external usage cost and an adapter to isolate response shape changes.

### D4 — Manual bounded tool loop, not an agent framework

Use `bind_tools` to expose only `web_search`. The backend reads `AIMessage.tool_calls`, validates arguments, executes the search, appends matching `ToolMessage` objects and invokes the model again as needed. Enforce hard caps: 3 search executions, 4 model calls, 5 results per search, finite total deadline. If model asks for multiple calls, respond to each requested call with a result or explicit budget/validation error, keeping tool-call IDs paired.

**Alternatives:** LangChain `create_agent`, LangGraph now, unrestricted recursive loop, provider-hosted web search.

**Rationale:** The student can see every step and understand the protocol before moving orchestration to LangGraph.

**Consequences:** More explicit message bookkeeping, but easier debugging and deterministic tests. Never trust the model to obey a cost limit without server-side enforcement.

### D5 — Request-scoped execution; no Phase 2 persistence

Expose two endpoints: `POST /api/v1/research/plan` and `POST /api/v1/research/discover`. Execute within the request and return typed results. Do not create research tables, workers or SSE.

**Alternatives:** Persist every plan and tool call; background jobs from day one.

**Rationale:** Keeps focus on LLM/tool mechanics; Phase 4/5 will establish durable workflow and UI progress.

**Consequence:** Long requests can be interrupted on disconnect/process restart; a bounded overall deadline limits exposure. Do not present this as production-grade job execution.

### D6 — Lazy credentials and test doubles

AI credentials remain optional at application startup. Return a safe `503` for missing provider configuration. Tests inject or mock model/search interfaces; no live provider calls in default CI. Manual live smoke tests require explicit opt-in.

**Alternatives:** Require keys at startup; run live provider tests in CI.

**Rationale:** Existing health checks and CI must work for contributors without paid credentials.

### D7 — Explicit safety and reliability limits

Validate user questions and tool arguments; allowlist tool names; do not fetch arbitrary URLs; treat snippets as untrusted; cap requests; use bounded retries only for transient errors; sanitize errors/logs. Do not infer source publication dates or report evidence not present in Tavily results.

**Alternatives:** Rely on prompt-only safeguards and provider defaults.

**Rationale:** Models can request unexpected actions and web content can contain adversarial instructions. Enforcement belongs to the application.

## Consequences

**Positive:** Small teachable vertical slice; minimal vendor abstraction; testable tool protocol; clean bridge to Phase 3 ingestion and Phase 4 LangGraph nodes.

**Negative:** No persistent execution, no comprehensive report, dependence on OpenAI and Tavily, two sets of provider failure modes.

## Compatibility with ADR-001

- Preserves Python 3.14, uv, modular FastAPI, app factory, optional AI settings and green CI.
- Reuses the existing `/api/v1` router and `core/config.py`.
- Does not touch SQLAlchemy, Alembic, PostgreSQL or Qdrant schema in this phase.
- Leaves the future durable worker decision open.

## Revisit triggers

- LangGraph replaces the manual tool loop in Phase 4.
- A second LLM/search provider becomes a real requirement.
- Actual cost/latency metrics justify multiple model tiers.
- PDF/RAG retrieval requires source IDs, passage-level provenance and persistent jobs.
- Deployment needs cancellation, durable state or distributed workers.
