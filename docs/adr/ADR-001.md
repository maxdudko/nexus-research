# ADR-001 — Python Backend Foundation and Infrastructure

**Status:** Accepted for Phase 1  
**Date:** 2026-10-10  
**Decision owners:** Nexus Research project

## Context

Nexus Research is a portfolio-grade learning product targeting autonomous web research and PDF-based RAG. The developer is experienced with TypeScript/NestJS but is building hands-on expertise in Python, FastAPI, SQLAlchemy, LangChain and LangGraph. The target is a two-week MVP; infrastructure complexity must remain bounded.

## Decisions

### D1. Python 3.14 + uv + `src/` package layout
Use Python 3.14, uv for dependencies/locking, and an installable `nexus` package under `apps/api/src/nexus`.

**Alternatives:** pip + venv + requirements.txt; Poetry; monorepo-wide Python workspace immediately.

**Rationale:** Modern reproducible tooling, idiomatic packaging, low configuration overhead. Avoid a workspace abstraction until multiple Python packages exist.

### D2. FastAPI modular monolith
Use one FastAPI application with API, core, and infrastructure modules. Keep route handlers thin. Prefer explicit composition and FastAPI dependencies to a custom IoC container.

**Alternatives:** Django/DRF; Flask; multiple services.

**Rationale:** Async-friendly API, Pydantic integration, OpenAPI and a smaller learning surface than distributed services.

### D3. PostgreSQL 18 + SQLAlchemy 2.0.x async + asyncpg + Alembic
Use SQLAlchemy's `AsyncEngine` and `async_sessionmaker`; sessions are scoped to one request or independently executed task. Manage schema changes with Alembic. No research tables in Phase 1.

**Alternatives:** synchronous SQLAlchemy; SQLModel; raw SQL; Prisma via TypeScript.

**Rationale:** Learn a widely used Python persistence stack and explicit transaction/session management. The 2.0.x line is pinned to reduce API churn during the initial learning phase.

**Consequence:** Async code requires careful handling of implicit IO, session ownership, test fixtures and migrations.

### D4. Qdrant for future RAG
Provision Qdrant locally in Phase 1, but defer collections, embeddings and retrieval until the RAG phase.

**Alternatives:** PostgreSQL + pgvector; Chroma; FAISS.

**Rationale:** Dedicated vector search learning and familiarity with retrieval infrastructure. Additional service overhead is acceptable for this learning project.

### D5. OpenAI as the only initial LLM provider
The MVP uses OpenAI for generation and embeddings in later phases. Phase 1 only reserves optional settings and does not install AI packages prematurely.

**Alternatives:** multi-provider abstraction from day one; BYOK.

**Rationale:** Fewer integration variables and faster diagnosis while learning LangChain/LangGraph. A narrow provider boundary may be introduced when AI functionality exists.

### D6. Docker Compose for data services; API runs via uv locally
Provision PostgreSQL and Qdrant using Docker Compose. Run FastAPI directly through uv for fast debugging; containerizing the API is deferred until release.

**Alternatives:** full containerized development; managed cloud databases.

**Rationale:** Faster feedback for Python debugging and minimal cost.

### D7. Testing and code quality are required from the start
Use pytest, pytest-asyncio, HTTPX, Ruff and mypy. Separate unit tests from integration tests and isolate integration databases.

**Alternatives:** defer tests; use only end-to-end tests.

**Rationale:** Early testing catches async lifecycle and configuration errors before LangGraph complexity arrives.

### D8. No production job queue in Phase 1
Long-running research execution is explicitly deferred. Future phases must distinguish research job lifetime from SSE connection lifetime and decide on recovery/retries before public deployment.

**Alternatives:** introduce Celery/Redis now; FastAPI BackgroundTasks as a permanent job engine.

**Rationale:** Neither a production queue nor in-process background tasks are necessary for backend bootstrap. Avoid treating process-local tasks as durable execution.

## Consequences

**Positive:** Focused Python learning; reproducible local setup; clear boundaries; migration-ready storage; extensible foundation for agentic RAG.

**Negative:** Two local data services; async session learning curve; Qdrant adds operational overhead; future background execution requires a separate decision.

## Revisit triggers

- Research workflow needs durable execution or multiple API replicas.
- Multi-user access requires authentication and data isolation.
- Retrieval evaluations suggest pgvector or hybrid search is a better fit.
- Dependency upgrades require adopting SQLAlchemy 2.1+ or another Python runtime.
- Real provider requirements justify a multi-provider adapter.
