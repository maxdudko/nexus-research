# ADR-008 — Alpha Identity, Sessions and Research Ownership

**Status:** Proposed — not accepted  
**Date:** 2026-10-22  
**Target:** Phase 8 / Alpha `v0.2.0`  
**Related:** [`Phase 8 spec`](../specs/phase-8-identity/spec.md), [`Phase 8 plan`](../specs/phase-8-identity/plan.md), [`Alpha vision`](../specs/alpha-v0.2.0-vision.md), ADR-004/005/007

## Context

The `v0.1.0` MVP runs as a private single-operator app. All research endpoints are anonymous. `research_id` scopes PostgreSQL sources and Qdrant evidence but is not a user identity or authorization boundary. Run history is global. The Next.js same-origin API proxy does not forward cookies. LangGraph checkpoints use `run_id` as thread ID and are not automatically resumed.

Phase 8 requires independent invited users while preserving the current research engine and learning-focused Python stack. Public SaaS, organizations and enterprise auth are not requirements.

The decisions below are **recommendations for review**, not implemented or accepted facts.

## D1 — Local identity for a controlled Alpha

**Proposed decision:** use a minimal application-owned `User` model and controlled operator provisioning. Email is a normalized login identifier; accounts have `user`/`admin` role and active/disabled state. Do not expose public signup.

**Why:** smallest testable multi-user foundation; allows hands-on FastAPI, SQLAlchemy and security work without an external service dependency.

**Alternatives:** managed auth provider (lower credential-maintenance burden, but integration/vendor dependency); Next.js-only auth (would still require trusted principal propagation to FastAPI); OAuth/SSO (deferred).

**Risk:** operating passwords and sessions is security-sensitive. A managed provider may be preferable before public exposure. Revisit this decision if the Alpha becomes public.

## D2 — Password hashing and credential administration

**Proposed decision:** use a maintained Argon2id password-hashing implementation with library-managed salts and configurable parameters; no custom cryptography. Bootstrap the initial admin and invited users via an operator CLI that never prints or stores plaintext passwords. Allow an operator-controlled credential reset. No default credentials.

**Why:** appropriate for an invite-only Alpha without email delivery infrastructure.

**Alternatives:** magic links/email reset (requires secure email delivery); external identity provider (see D1). Do not implement homemade hashing, reversible password encryption or security questions.

**Review before acceptance:** exact library/version, parameter policy, hash upgrades, password minimum, reset audit trail, handling of compromised sessions.

## D3 — Opaque, revocable server-side browser sessions

**Proposed decision:** issue cryptographically random opaque session tokens in a host-only, `HttpOnly` cookie. Persist **only a keyed verifier/hash** of the token in PostgreSQL with user FK, expiration and revocation metadata. Resolve the authenticated principal on every request; check account status. Explicit logout revokes the current session. Use `Secure` in HTTPS, `SameSite=Lax` as a baseline, and an explicitly documented local HTTP loopback exception. Never expose raw tokens to JavaScript.

**Why:** immediate revocation, simple role updates and minimal authorization claims at the browser boundary.

**Alternatives:** JWT access/refresh tokens (more token lifecycle/revocation complexity for this small app); in-memory sessions (not durable and unsafe across restarts); Next.js-only session without FastAPI verification (rejected).

**Trade-offs:** an extra DB read/cache strategy and session storage/cleanup. Set bounded absolute and idle expiry; do not create perpetual sessions.

## D4 — Same-origin proxy and CSRF are part of auth

**Proposed decision:** retain Next.js as a same-origin API proxy. Explicitly forward only the intended session cookie and CSRF/Origin headers to FastAPI; propagate validated `Set-Cookie` responses, including clearing cookies on logout. Do not forward arbitrary browser cookies or credentials. Protect state-changing cookie-authenticated routes against CSRF using a documented token/origin strategy, including `multipart/form-data` and POST SSE. Avoid caching authenticated responses.

**Why:** `apps/web/src/lib/proxy.ts` currently strips cookies; merely adding FastAPI login would not authenticate subsequent proxied calls.

**Alternatives:** browser-direct API with CORS/credential configuration (increases exposure and complexity); bearer tokens in localStorage (rejected for browser session design).

**Review before acceptance:** precise CSRF design, trusted host/origin policy, cookie Path/Domain, HTTPS termination and development loopback behavior. `SameSite` alone is not the complete CSRF policy.

## D5 — `ResearchScope` is the authorization root

**Proposed decision:** create `ResearchScope(research_id, owner_user_id)` in PostgreSQL. `ResearchRun` and `Source` refer to that scope; `ResearchReportRecord` inherits access through its run. `research_id` remains globally unique and preserves existing evidence semantics. The API server creates new scopes; a caller may reuse only an already-owned scope. Add an explicit scope creation endpoint for PDF-first workflows.

**Why:** avoids duplicating ownership across every table, preserves existing Qdrant payload and deduplication rules, and leaves room for a later workspace ownership model.

**Alternatives:** `user_id` on each run/source independently (duplicated authority, inconsistent ownership risk); `user_id` embedded in client IDs or Qdrant only (not a secure authorization source); full organization/workspace tenancy (deferred).

**Trade-offs:** joins for owner-filtered queries and one additional table/API. Index by owner; foreign keys enforce scope integrity. Revisit performance after measurement, not preemptively.

## D6 — PostgreSQL authorization before Qdrant and graph access

**Proposed decision:** resolve `CurrentUser` from the session and authorize scope/run access in the API/service layer before any embedding, Qdrant query/upsert, provider call or checkpoint read. `research_id` and `run_id` are untrusted selectors. For foreign or missing private resources return indistinguishable `404` responses. Admin does not bypass normal research ownership automatically.

**Why:** Qdrant filters prevent mixing evidence between scopes, but cannot decide who may access a scope. A graph thread ID is not an access credential.

**Alternatives:** PostgreSQL RLS as the sole enforcement layer (does not protect Qdrant/provider calls; could be considered defense in depth later); Qdrant `user_id` payload as sole auth (rejected); handler-only checks (fragile and easy to omit).

**Trade-offs:** service-layer authorization requires disciplined interfaces and integration tests. No direct public Qdrant or checkpoint endpoints.

## D7 — Legacy data is quarantined, never silently claimed

**Proposed decision:** during upgrade, create scopes for distinct legacy `research_id` values and assign them to a permanently disabled, non-loginable legacy identity. Preserve existing runs, sources, reports and Qdrant points. Provide an explicit operator-only adoption command that reassigns selected scopes to a real user after review; log scope IDs and destination identity, never content or secrets.

**Why:** preserves unattended schema initialization and data while avoiding accidental disclosure to the first registered account.

**Alternatives:** delete old data (rejected); assign to first admin automatically (rejected); leave nullable owner indefinitely (weakens ownership invariant); require manual pre-upgrade migration (more operational friction, acceptable fallback if quarantine implementation is unsafe).

**Trade-offs:** migration and CLI are more involved. Prove fresh install, upgraded data, idempotence and failed-upgrade recovery. Do not promise a safe automatic downgrade after owner assignment.

## D8 — Minimal roles, private deployment and cost controls

**Proposed decision:** keep only `user` and `admin`. Admin-only actions require explicit `require_admin`; normal research endpoints remain owner-scoped for admins too. Maintain loopback/private deployment and operator-funded provider keys. Add explicit authentication throttling and bounded per-user billable operations before inviting users. Keep existing process-wide stream bound and document its worker-local semantics; enforce stronger cross-worker limits if deployment uses multiple workers.

**Why:** authorization and billable endpoints must be safe together. Authentication without cost control is not an invitation-ready product.

**Alternatives:** organizations and enterprise RBAC (deferred); anonymous trial (rejected for this phase); unlimited authenticated research (rejected).

## D9 — Preserve existing execution and evaluation contracts

**Proposed decision:** do not introduce background workers, auto-resume, multi-provider auth or Phase 10 evaluation UI. The synchronous `/run` path remains a distinct execution path unless separately specified. Existing checkpoint and report formats are not modified for user identity unless necessary to enforce ownership.

**Why:** isolates security migration risk and keeps the existing research baseline testable.

## Consequences and acceptance conditions

**Positive:** server-enforced ownership, revocable sessions, clear two-user tests, compatibility with the existing general-purpose research engine.

**Negative:** credential security responsibility, new session DB operations, migration complexity and more integration tests.

**ADR can be accepted only after:** (1) authentication/CSRF threat review, (2) exact migration/backfill test design, (3) full endpoint authorization matrix, (4) proxy/SSE test design, (5) defined cost/rate policy and deployment topology. Approval of this ADR is not a claim that the implementation is secure; Phase 8 review gates must verify it.
