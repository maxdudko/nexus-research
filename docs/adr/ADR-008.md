# ADR-008 — Alpha Identity, Sessions and Research Ownership

**Status:** Accepted  
**Date:** 2026-10-22  
**Accepted:** 2026-10-22 — Gate 0, [`gate-0.md`](../specs/phase-8-identity/gate-0.md)  
**Target:** Phase 8 / Alpha `v0.2.0`  
**Related:** [`Phase 8 spec`](../specs/phase-8-identity/spec.md), [`Phase 8 plan`](../specs/phase-8-identity/plan.md), [`Alpha vision`](../specs/alpha-v0.2.0-vision.md), ADR-004/005/007

## Context

The `v0.1.0` MVP runs as a private single-operator app. All research endpoints are anonymous. `research_id` scopes PostgreSQL sources and Qdrant evidence but is not a user identity or authorization boundary. Run history is global. The Next.js same-origin API proxy does not forward cookies. LangGraph checkpoints use `run_id` as thread ID and are not automatically resumed.

Phase 8 requires independent invited users while preserving the current research engine and learning-focused Python stack. Public SaaS, organizations and enterprise auth are not requirements.

The decisions below were **accepted at Gate 0** after review of the `v0.1.0` implementation on `development`. They are not yet implemented. Normative parameters are in [Accepted contract](#accepted-contract). Approval of this ADR is not a claim that the implementation is secure.

## D1 — Local identity for a controlled Alpha

**Decision:** use a minimal application-owned `User` model and controlled operator provisioning. Email is a normalized login identifier; accounts have `user`/`admin` role and active/disabled state. Do not expose public signup.

**Why:** smallest testable multi-user foundation; allows hands-on FastAPI, SQLAlchemy and security work without an external service dependency.

**Alternatives:** managed auth provider (lower credential-maintenance burden, but integration/vendor dependency); Next.js-only auth (would still require trusted principal propagation to FastAPI); OAuth/SSO (deferred).

**Risk:** operating passwords and sessions is security-sensitive. A managed provider may be preferable before public exposure. Revisit this decision if the Alpha becomes public.

## D2 — Password hashing and credential administration

**Decision:** use a maintained Argon2id password-hashing implementation with library-managed salts and configurable parameters; no custom cryptography. Bootstrap the initial admin and invited users via an operator CLI that never prints or stores plaintext passwords. Allow an operator-controlled credential reset. No default credentials.

**Why:** appropriate for an invite-only Alpha without email delivery infrastructure.

**Alternatives:** magic links/email reset (requires secure email delivery); external identity provider (see D1). Do not implement homemade hashing, reversible password encryption or security questions.

**Accepted parameters:** `argon2-cffi` `PasswordHasher` with `time_cost=3`, `memory_cost=65536`, `parallelism=4`, `hash_len=32`, `salt_len=16`, type Argon2id. Rehash on successful login when `check_needs_rehash` is true. Passwords are 12–128 characters, read from stdin by the operator CLI, and never logged. Reset and disable revoke every session for that user. See the accepted contract.

## D3 — Opaque, revocable server-side browser sessions

**Decision:** issue cryptographically random opaque session tokens in a host-only, `HttpOnly` cookie. Persist **only a keyed verifier/hash** of the token in PostgreSQL with user FK, expiration and revocation metadata. Resolve the authenticated principal on every request; check account status. Explicit logout revokes the current session. Use `Secure` in HTTPS, `SameSite=Lax` as a baseline, and an explicitly documented local HTTP loopback exception. Never expose raw tokens to JavaScript.

**Why:** immediate revocation, simple role updates and minimal authorization claims at the browser boundary.

**Alternatives:** JWT access/refresh tokens (more token lifecycle/revocation complexity for this small app); in-memory sessions (not durable and unsafe across restarts); Next.js-only session without FastAPI verification (rejected).

**Trade-offs:** an extra DB read/cache strategy and session storage/cleanup. Set bounded absolute and idle expiry; do not create perpetual sessions.

## D4 — Same-origin proxy and CSRF are part of auth

**Decision:** retain Next.js as a same-origin API proxy. Explicitly forward only the intended session cookie and CSRF/Origin headers to FastAPI; propagate validated `Set-Cookie` responses, including clearing cookies on logout. Do not forward arbitrary browser cookies or credentials. Protect state-changing cookie-authenticated routes against CSRF using a documented token/origin strategy, including `multipart/form-data` and POST SSE. Avoid caching authenticated responses.

**Why:** `apps/web/src/lib/proxy.ts` currently strips cookies; merely adding FastAPI login would not authenticate subsequent proxied calls.

**Alternatives:** browser-direct API with CORS/credential configuration (increases exposure and complexity); bearer tokens in localStorage (rejected for browser session design).

**Accepted parameters:** cookies `nexus_session` (HttpOnly) and `nexus_csrf` (double-submit, not HttpOnly), `Path=/`, no `Domain`, `SameSite=Lax`. `Secure` is required in production unless `NEXUS_COOKIE_INSECURE_LOOPBACK=true`. Unsafe cookie-authenticated requests require an allowlisted `Origin` and `X-CSRF-Token`. `SameSite` is not the CSRF policy. See the accepted contract.

## D5 — `ResearchScope` is the authorization root

**Decision:** create `ResearchScope(research_id, owner_user_id)` in PostgreSQL. `ResearchRun` and `Source` refer to that scope; `ResearchReportRecord` inherits access through its run. `research_id` remains globally unique and preserves existing evidence semantics. The API server creates new scopes; a caller may reuse only an already-owned scope. Add an explicit scope creation endpoint for PDF-first workflows.

**Why:** avoids duplicating ownership across every table, preserves existing Qdrant payload and deduplication rules, and leaves room for a later workspace ownership model.

**Alternatives:** `user_id` on each run/source independently (duplicated authority, inconsistent ownership risk); `user_id` embedded in client IDs or Qdrant only (not a secure authorization source); full organization/workspace tenancy (deferred).

**Trade-offs:** joins for owner-filtered queries and one additional table/API. Index by owner; foreign keys enforce scope integrity. Revisit performance after measurement, not preemptively.

## D6 — PostgreSQL authorization before Qdrant and graph access

**Decision:** resolve `CurrentUser` from the session and authorize scope/run access in the API/service layer before any embedding, Qdrant query/upsert, provider call or checkpoint read. `research_id` and `run_id` are untrusted selectors. For foreign or missing private resources return indistinguishable `404` responses. Admin does not bypass normal research ownership automatically.

**Why:** Qdrant filters prevent mixing evidence between scopes, but cannot decide who may access a scope. A graph thread ID is not an access credential.

**Alternatives:** PostgreSQL RLS as the sole enforcement layer (does not protect Qdrant/provider calls; could be considered defense in depth later); Qdrant `user_id` payload as sole auth (rejected); handler-only checks (fragile and easy to omit).

**Trade-offs:** service-layer authorization requires disciplined interfaces and integration tests. No direct public Qdrant or checkpoint endpoints.

## D7 — Legacy data is quarantined, never silently claimed

**Decision:** during upgrade, create scopes for distinct legacy `research_id` values and assign them to a permanently disabled, non-loginable legacy identity. Preserve existing runs, sources, reports and Qdrant points. Provide an explicit operator-only adoption command that reassigns selected scopes to a real user after review; log scope IDs and destination identity, never content or secrets.

**Why:** preserves unattended schema initialization and data while avoiding accidental disclosure to the first registered account.

**Alternatives:** delete old data (rejected); assign to first admin automatically (rejected); leave nullable owner indefinitely (weakens ownership invariant); require manual pre-upgrade migration (more operational friction, acceptable fallback if quarantine implementation is unsafe).

**Trade-offs:** migration and CLI are more involved. Prove fresh install, upgraded data, idempotence and failed-upgrade recovery. Do not promise a safe automatic downgrade after owner assignment.

## D8 — Minimal roles, private deployment and cost controls

**Decision:** keep only `user` and `admin`. Admin-only actions require explicit `require_admin`; normal research endpoints remain owner-scoped for admins too. Maintain loopback/private deployment and operator-funded provider keys. Add explicit authentication throttling and bounded per-user billable operations before inviting users. Keep the existing process-wide stream bound. Phase 8 supports one API process only, so those process-local limits are the instance limits. A deployment with multiple API processes is unsupported and requires a new review.

**Why:** authorization and billable endpoints must be safe together. Authentication without cost control is not an invitation-ready product.

**Alternatives:** organizations and enterprise RBAC (deferred); anonymous trial (rejected for this phase); unlimited authenticated research (rejected).

## D9 — Preserve existing execution and evaluation contracts

**Decision:** do not introduce background workers, auto-resume, multi-provider auth or Phase 10 evaluation UI. The synchronous `/run` path remains a distinct execution path unless separately specified. Existing checkpoint and report formats are not modified for user identity unless necessary to enforce ownership.

**Why:** isolates security migration risk and keeps the existing research baseline testable.

## Consequences and acceptance conditions

**Positive:** server-enforced ownership, revocable sessions, clear two-user tests, compatibility with the existing general-purpose research engine.

**Negative:** credential security responsibility, new session DB operations, migration complexity and more integration tests.

Gate 0 completed the authentication/CSRF threat review, migration/backfill test design, endpoint authorization matrix, proxy/SSE test design, and cost/rate policy for the single-process topology. Those records are in [`gate-0.md`](../specs/phase-8-identity/gate-0.md). Later Phase 8 gates must still verify the implementation. This acceptance does not authorize public deployment or tag `v0.2.0`.

## Accepted contract

These parameters are normative for Phase 8. They close spec decisions 1–7.

### Identity and passwords

- Library: `argon2-cffi`, parameters above. No homemade hashing and no default password.
- Email is trimmed and lowercased, at most 254 characters, and unique via a partial unique index where email is not null. The quarantine identity has no email.
- Account status is `active`, `disabled`, or `quarantine`. Only `active` can authenticate. `quarantine` cannot be moved to `active`.
- CLI, passwords on stdin only: `python -m nexus.identity bootstrap-admin`, `create-user`, `disable-user`, `reset-password`, `adopt-scope`. `bootstrap-admin` creates the first admin and later exits 0 without changing that password or creating another admin. There is no public registration and no HTTP user-admin API in this phase.
- Audit log event `identity.audit` records the action, target user id, and scope id for adoption. It does not record passwords, tokens, questions, PDF text, or source excerpts.

### Sessions, cookies, and CSRF

- Session token: 32 cryptographically random bytes, URL-safe in the cookie. PostgreSQL stores only HMAC-SHA256 of the token keyed with `NEXUS_SESSION_PEPPER` (required, at least 32 bytes, distinct from the database password). Lookup is by that unique hash. Compare with `hmac.compare_digest`.
- Absolute lifetime 12 hours, set at creation and never extended. Idle lifetime 4 hours from `last_used_at`. `last_used_at` advances at most once per five minutes. Logout revokes only the presented session.
- Cookie `Secure`: true when `NEXUS_ENVIRONMENT=production`. Production startup fails if `NEXUS_COOKIE_SECURE=false` unless `NEXUS_COOKIE_INSECURE_LOOPBACK=true`. Development and test may leave `Secure` unset. The current private release stack is HTTP on `127.0.0.1` and must set the loopback exception explicitly. Phase 8 does not add TLS.
- `NEXUS_TRUSTED_ORIGINS` is an exact origin list. Production must set it and fails closed when empty. Development default is `http://127.0.0.1:3000` and `http://localhost:3000`.
- `POST /auth/login` requires a matching `Origin` and does not require a CSRF token. Every other unsafe method that presents `nexus_session` requires a matching `Origin` and an `X-CSRF-Token` equal to `nexus_csrf`. Missing or mismatched CSRF is rejected before any state change. `GET /auth/me` is cookie-only.
- Auth responses send `Cache-Control: no-store`. Login failure is HTTP 401, code `invalid_credentials`, message `The email or password is incorrect.`, for unknown and wrong passwords. Other missing or unusable sessions are HTTP 401, code `unauthenticated`, message `Authentication is required.`

### Proxy

The Next.js proxy forwards request headers `content-type`, `accept`, `origin`, and `x-csrf-token`, plus a `cookie` header reduced to `nexus_session` and `nexus_csrf`. It forwards response headers `content-type`, `cache-control`, `x-accel-buffering`, and `set-cookie` only for those two cookie names, using a multi-value `Set-Cookie` append. It keeps the unbuffered POST body and abort path. It does not forward `authorization` or any other cookie.

### Ownership

- `POST /api/v1/research/scopes` has no client id. It inserts a server-generated `research_id` owned by the current user and returns that id.
- Omitted `research_id` on `/research/run` and `/research/stream` mints a scope the same way. A supplied id is used only after a lookup of `(research_id, owner = current user)`. Missing and foreign ids return the existing envelope `not_found` / `The research run was not found.` with no body echo of the id, and they create no scope, run, permit, or provider call.
- Evidence routes require an existing owned scope. They do not mint one.
- No request body `user_id` or role is authoritative. Admin does not skip ownership. `require_admin` is a dependency for tests and later Phase 10 routes; a normal user receives HTTP 403, code `forbidden`.
- Private route dependencies must resolve the principal before a dependency opens Qdrant, the checkpointer, or an ingestion/retrieval service. An unauthorized request must not take the stream semaphore or insert history.
- `/health/live` and `/health/ready` stay anonymous and must not gain user, secret, or research fields. Compose continues to call `/ready` on the internal API network.

### Migration

- Quarantine user id `00000000-0000-4000-8000-000000000001`, null email, null password hash, role `user`, status `quarantine`. The migration inserts this row on both fresh install and upgrade.
- One Alembic revision, in a transaction: create `users`, `auth_sessions`, and `research_scopes`; insert the quarantine user; insert one scope per distinct `research_id` in `research_runs` and `sources`; add `ON DELETE RESTRICT` foreign keys from those `research_id` columns and from scope owner to `users`. Do not alter report JSON, Qdrant payloads, or LangGraph checkpoint tables.
- `adopt-scope` reassigns a scope only while its owner is the quarantine user. It refuses real-user owners and refuses the quarantine user as the destination.
- `downgrade()` of this revision drops the new foreign keys, `research_scopes`, `auth_sessions`, and `users` without deleting runs, reports, or sources, and only while every scope is still owned by the quarantine user. Otherwise it aborts. Operator rollback remains the cold backup restore in `docs/release/operations.md`. Downgrade does not touch Qdrant or checkpoints.

### Topology, quotas, and live streams

- Approved topology: one API container, one uvicorn process, no `--workers`, as in `apps/api/Dockerfile` and `compose.release.yml`. Phase 8 limits are process-local and are therefore instance limits only under that topology. Multiple API processes are unsupported.
- Keep `NEXUS_STREAM_MAX_CONCURRENT` (default 2, maximum 8) as the process-wide stream cap. Add a per-user cap of one active `/stream` and one active `/run`.
- Add a per-user limit of 10 requests per 60 seconds shared by `/plan`, `/discover`, `/run`, `/stream`, `/evidence/web`, `/evidence/pdf`, and `/evidence/search`. Scope mint is separate: 30 per hour per user. Excess is HTTP 429, code `too_many_requests`, with `Retry-After`, and no provider call.
- Login throttle, also process-local: 5 failures per 15 minutes per normalized email and 30 per 15 minutes per client IP, then 429. Unknown emails still run a dummy Argon2 verify against a hash generated at process start. A restart clears counters. That residual risk is accepted for this private single-process deployment and must be revisited before public exposure.
- An active stream re-reads session revocation and account status at each heartbeat and before a graph node that would call a provider. Failure cancels the run through the existing interrupt path (`status=interrupted`, `error_code=interrupted`). The residual window is the current heartbeat interval plus a provider call that has already started, still bounded by the existing graph deadline. No cross-process kill is added.

### Browser path

Phase 8 includes a minimal `/login` page, an account strip fed by `GET /auth/me`, logout, and a redirect of unauthenticated `/` to `/login`. The research page mints a scope before PDF upload. Phase 9 owns the application shell. Users are not invited at Gate A.
