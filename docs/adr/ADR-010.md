# ADR-010 — Admin Control Plane, Evaluation Provenance, and Privacy

**Status:** Accepted  
**Date:** 2026-10-24  
**Accepted:** 2026-10-24 — Gate 0, [`gate-0.md`](../specs/phase-10-admin-evaluation/gate-0.md)  
**Target:** Nexus Research Alpha `v0.2.0` / Phase 10  
**Related:** [Phase 10 specification](../specs/phase-10-admin-evaluation/spec.md), [plan](../specs/phase-10-admin-evaluation/plan.md), [ADR-006](ADR-006.md), [ADR-008](ADR-008.md), [ADR-009](ADR-009.md), [evaluation methodology](../evaluation/methodology.md)

## Context

Nexus Research has a deterministic fixture-based evaluation suite, a separately opted-in live grounding judge, an existing `calibrate` function, and limited usage/cost instrumentation. Results are currently JSON artifacts, not an immutable queryable history. The Phase 8 `require_admin` dependency provides role authorization, and Phase 9 provides a shared authenticated UI shell. The system stores user-owned research and must not turn platform administration into cross-user content access.

Four choices have been approved: CLI execution + DB import, PostgreSQL run/case history, aggregate/safe-metadata-only admin access, and basic usage/cost reporting with coverage. This ADR resolves the resulting implementation contracts.

## Decision D1 — CLI-only evaluation execution; import as a separate boundary

- Keep `python -m nexus.evaluation --suite offline|live --output ...` unchanged, including the `NEXUS_RUN_LIVE_AI=1`, `--max-cases`, API key, and published-rate warnings for live judge.
- Introduce a **local operator import command** (proposed `python -m nexus.admin.evaluation_import --artifact ... --fixtures ...`). It performs no provider calls. Do not expose import or evaluation execution through HTTP, and do not add a background job framework in Alpha.
- Import is a privileged **operational action**: require filesystem/DB operator access, not merely an authenticated browser session. Document who may run it and never expose DB credentials to the frontend.
- Validate input before opening a write transaction: bounded file size, supported report schema/version, case identities and outcomes, internally consistent aggregates, dataset fingerprint and offline re-execution or live calibration recomputation.

**Why:** reuses the tested CLI and avoids paid/unbounded work in web requests.  
**Trade-off:** operator must run/import artifacts manually; no real-time evaluation scheduler.  
**Rejected:** HTTP-triggered live judge, arbitrary JSON upload from browser, scheduled workers.

## Decision D2 — Two-table, immutable evaluation history

Add `evaluation_runs` and `evaluation_case_results` via SQLAlchemy/Alembic. A run records suite, outcome, dataset version and SHA-256 fingerprint, report/scorer versions, K, optional judge/model/prompt/config, optional code revision, import/execution timestamps, artifact SHA-256, provenance level, and bounded summary JSONB. A case records category, semantic case ID and a bounded, allowlisted JSONB result.

- Unique artifact hash; composite case key `(evaluation_run_id, category, case_id)`; indexed descending history.
- All inserts atomic. Reimport same bytes/metadata returns existing ID; conflicting metadata for the same artifact hash fails; existing results are never overwritten.
- Use an explicit `scorer_version` separate from `report_version`. Changes in formulas, denominators, undefined-case treatment, label taxonomy, or rounding rules require a scorer-version review/bump.
- Do not add foreign keys to `users`, `research_runs`, or `research_scopes`: these evaluations are based on authored fixtures, not private user data.
- Only curated metrics/labels/codes are stored. Do not store the original artifact JSON wholesale or free-text `rationale`, claims, questions, excerpts, source URLs, prompts, or API credentials.

**Why:** supports repeatable comparisons and queryable history without creating a sensitive corpus of private research.  
**Trade-off:** no raw text inspection from admin UI; original operator fixture/artifact remains the source for deep debugging outside the web app.  
**Rejected:** JSON-file-only history; unrestricted JSONB copy of entire artifacts; event sourcing.

## Decision D3 — Explicit provenance and legacy limitations

- Compute `dataset_sha256` from a canonical ordered manifest of the five validated fixture files. A human-readable `dataset_version` alone is not sufficient to prove identical inputs.
- Compute `artifact_sha256` from the exact source bytes.
- For **offline** imports, recompute the current deterministic suite with the supplied fixtures and require equality to the imported normalized report; label `offline_recomputed`. This verifies compatibility with the importer environment, **not** the historical execution date or original code commit.
- For **live** imports, validate and recompute counts/calibration from stored labels; label `operator_imported`. Do not claim to cryptographically verify that the provider was called or that predictions came from the declared model.
- Legacy artifacts without reliable timestamps/commit metadata store `executed_at = null` and `code_revision = null` unless separately provided with documented operator provenance. `imported_at` must not be presented as execution time.
- Importing the committed offline baseline requires exact committed artifact bytes plus successful fixture verification. Do not change the baseline file or the existing CI byte gate.

**Why:** prevents fabricated history and false confidence from a plausible-looking JSON file.  
**Trade-off:** imported legacy runs have incomplete provenance and may need warning labels.  
**Rejected:** infer commit from current branch or execution time from file mtime; accept a matching dataset version without fingerprint.

## Decision D4 — Strict comparison semantics

A comparison is allowed only when the following match:

- Both suites, dataset SHA-256 and version, report version, scorer version, K, and metric contract.
- For live judge comparisons, additionally model, prompt version, temperature, judge parameters and label taxonomy.

The `code_revision` may differ: detecting regressions between revisions is a core use case. An unknown revision is a provenance warning, not a fabricated value. Different pricing versions invalidate direct *cost* comparisons but do not by themselves invalidate judge-label agreement.

For incompatible pairs, return `comparable=false`, reason codes and no metric deltas. The UI may display raw metrics side-by-side under a clear incompatibility warning. For compatible pairs, compute numeric deltas with Decimal from stored canonical metrics. Offline metrics are fixture regression indicators only; live judge agreement/matrix is informational on an authored labeled set, not real-world truth accuracy. Skipped/failed live cases are excluded from the confusion matrix.

**Why:** without strict comparability, a dataset or judge change can masquerade as an improvement.  
**Trade-off:** fewer pairs receive a delta; exploratory comparisons remain descriptive.  
**Rejected:** compare every pair by `dataset_version` string alone; call live judge agreement an accuracy guarantee.

## Decision D5 — Read-only, privacy-minimized admin control plane

- Use existing `require_admin` FastAPI dependency on **every** `/api/v1/admin/*` route. Standard accounts get `403`; anonymous sessions get `401`.
- Add `/admin` to the existing Phase 9 authenticated shell. UI role checks are navigation affordances only.
- Admin may view authored evaluation metadata/case labels and aggregated run health, but does not inherit another user's `ResearchScope` ownership. Existing owner-scoped research endpoints remain unchanged.
- Admin research diagnostics select allowlisted columns only: opaque run ID if needed, status, sanitized error code, timestamps and derived duration. Do not include question, report, user email, user ID, research ID, source content, or raw traces.
- Return `Cache-Control: no-store`, bounded time windows and pagination. Do not add arbitrary filter-by-user or report-drilldown endpoints. No secrets, tokens, raw prompts or sensitive text in logs, traces, error bodies or client storage.

**Why:** operations visibility should not weaken the isolation guaranteed by Phase 8.  
**Trade-off:** some deep troubleshooting remains an operator-side, controlled workflow outside the admin UI.  
**Rejected:** superuser bypass of all research endpoints, ORM-to-JSON serialization, generic SQL explorer.

## Decision D6 — Basic diagnostics; unknown costs remain unknown

- Use `research_runs` for aggregate statuses, error-code counts, and elapsed durations where both timestamps exist. Stale `running` means *last recorded running*, not confirmed execution.
- Read only durable usage fields already available. `ResearchRun.usage` holds graph usage, not a complete provider billing ledger. The request-scoped `UsageBuffer` and log summary do not automatically become historical accounting records.
- Cost fields are nullable. `coverage=unavailable` and `amount=null` when source observations are missing; never substitute `$0.00`. When a persisted estimate is genuinely available, preserve pricing version, USD currency, coverage, unknown-operation count, and estimate disclaimer.
- No log scraping for authoritative historical costs, no new usage ledger, and no billing/chargeback in Alpha.

**Why:** honest incomplete telemetry is more useful than a precise-looking invented number.  
**Trade-off:** initial Admin Usage may show operation/run counts but no dollar totals for historical research.  
**Rejected:** derive provider spend from `llm_calls` or multiply run count by a guessed average.

## Decision D7 — Small modules, not a new platform

Proposed boundaries (paths illustrative):

```text
apps/api/src/nexus/
  evaluation/                  # Existing pure scoring, judge, result schemas
  admin/
    evaluation_import.py       # Operator CLI adapter; no HTTP import
    evaluation_store.py        # Async SQLAlchemy repository
    comparison.py              # Pure compatibility + Decimal deltas
    diagnostics.py             # Read-only aggregate queries
    schemas.py                 # Strict admin response DTOs
  models/evaluation.py         # Two new SQLAlchemy models
  api/v1/admin.py              # require_admin protected read-only router

apps/web/src/
  app/(app)/admin/...          # Existing authenticated shell
  components/admin/...        # Tables, matrix, coverage indicators
  lib/admin-api.ts             # Typed fetch client; no new auth stack
```

Use the existing Next.js proxy and API client. Keep the evaluation engine independent of FastAPI, persistence and web UI; avoid a new global frontend store, analytics platform, or background worker.

## Accepted contract

These parameters were fixed at Gate 0 after reading `development` at `9fb4f096606f59f61f47713c8f8f7f0b71e7c4c5`. The evidence is in [`gate-0.md`](../specs/phase-10-admin-evaluation/gate-0.md). They close the technical checks. They do not close Phase 9 Gate C, tag `v0.2.0`, or approve a public deployment.

### C1 — Versions and hashes

- `SCORER_VERSION = "1"` is a new constant beside `REPORT_VERSION` in `evaluation/schemas.py`. The importer stamps it. It is not a field on `OfflineReport` or `LiveReport`, and `dump_report` stays byte-compatible with `docs/evaluation/baseline.json`.
- Scorer `1` means the current retrieval contract: `QUANT = 0.000001`, empty gold is null and excluded from the macro average, precision uses `K` as the denominator, MRR is `0` when the top `K` has no hit, and the aggregate averages the already-rounded case strings. It also means the current calibration contract: labels in the order `supported`, `unsupported`, `insufficient_context`, `contradictory`; rows are gold and columns are predicted; a case is excluded when `outcome != "ok"` or `predicted_label` is null.
- `dataset_sha256` is the SHA-256 of a UTF-8 manifest. The manifest lists the five fixture files in lexicographic filename order. Each line is `{filename} {sha256_hex_of_raw_bytes}\n`. Extra files in the directory are ignored. A missing file fails dataset validation.
- `artifact_sha256` is the SHA-256 of the artifact file's original bytes. The maximum size is 2,097,152 bytes. The importer rejects a larger file before it parses JSON.

### C2 — Import command

The entry point is `python -m nexus.admin.evaluation_import`. It uses the same `Settings` database URL as `python -m nexus.identity`. There is no database-URL flag and no HTTP upload.

```text
uv run python -m nexus.admin.evaluation_import \
  --artifact PATH \
  [--fixtures DIR] \
  [--code-revision SHA] \
  [--committed-baseline]
```

- `--fixtures` defaults to `default_fixture_dir()`.
- `--code-revision` is a 40-hex Git SHA. Uppercase hex is stored lowercase. The source is `operator_asserted`. The importer does not run Git and does not read `HEAD`.
- `--committed-baseline` compares the artifact bytes with `docs/evaluation/baseline.json`, resolved as `Path(__file__).resolve().parents[5] / "docs" / "evaluation" / "baseline.json"` from `admin/evaluation_import.py`. The flag requires an offline artifact. A byte match plus offline recomputation sets `is_committed_baseline`. Without the flag the column stays false.
- Phase 10 accepts no execution-time flag. `executed_at` is null. `imported_at` is the insert clock in UTC.
- Offline imports call `run_offline` and require `model_dump(mode="json")` equality. Live imports recompute retrieval, citations, `judge_counts`, and `calibrate`, and require the fixture gold labels to match. Live provenance is `operator_imported`.
- One transaction inserts the run and its cases. Validation failure writes nothing. The same artifact hash with the same derived metadata returns the existing id and does not change `imported_at`. A difference in flags or fixture fingerprint is a conflict, not an update.
- Success prints only the UUID on stdout. Failures print a fixed sentence on stderr and do not print file contents, rationale, claims, or the database URL.

### C3 — Tables

Alembic head on this branch is `e3b7d91c4a20`. The next revision sets `down_revision` to that id and creates only `evaluation_runs` and `evaluation_case_results`.

`code_revision_source` is null, or `operator_asserted` when `code_revision` is set. Both are null or both are set. Live rows require `model`, `prompt_version`, `temperature`, and `pricing_version`. Offline rows require those four to be null. `temperature` is `NUMERIC`. Provenance matches the suite. `is_committed_baseline` implies an offline passed row with `offline_recomputed`.

`summary` and `config` are the allowlisted objects in the Gate 0 record. Case `result` objects are the allowlists there too. The database checks column shape. Pydantic checks JSON keys before insert. Downgrade drops these two tables and their rows. It does not change research, identity, Qdrant, or checkpoints. The source artifacts remain the copy an operator can import again.

### C4 — Comparison and routes

Quality comparison requires equal `suite`, `dataset_sha256`, `dataset_version`, `report_version`, `scorer_version`, and `k`. Live pairs also require equal `model`, `prompt_version`, `temperature`, and `label_taxonomy`. Reason codes, in this order, are `suite_mismatch`, `dataset_mismatch`, `report_version_mismatch`, `scorer_mismatch`, `k_mismatch`, and `judge_config_mismatch`. The last code is considered only when both suites are live.

`comparable: false` omits metric deltas and matrix deltas. The response still includes each side's stored headline metrics. A null stored metric produces a null delta even when the pair is comparable. Deltas are `Decimal` strings quantized to `0.000001`, computed as right minus left. `code_revision` may differ. Unknown execution time and unknown revision are warnings: `execution_time_unknown` and `code_revision_unknown`.

`cost_comparable` is a separate flag. It is true only when both `pricing_version` values are present and equal. Otherwise the reason is `pricing_unavailable` or `pricing_version_mismatch`. Phase 10 does not return a dollar delta.

Register `GET /evaluations/compare` before `GET /evaluations/{evaluation_id}`. Missing evaluations return 404 `not_found` with message `The evaluation was not found.` The body does not contain the id. Other errors use the existing `{error: {code, message}}` envelope. List limits default to 20 and cap at 50. Cursors are opaque version-1 keysets. Diagnostic windows default to the last 7 days, include `created_at` from `from` inclusive to `to` exclusive, and reject a span longer than 90 days. Stale `running` means `started_at` is older than 10 minutes. That threshold is the constant `STALE_RUNNING_AFTER` in `admin/diagnostics.py`.

### C5 — Privacy and shell

Every admin route depends on `require_admin`. Extend the existing no-store response wrapper from `/api/v1/auth` to `/api/v1/admin`, including error responses. Leave the proxy allowlists unchanged. The catch-all proxy already forwards `/api/v1/admin`.

Admin SQL selects an explicit column list. It does not select `question`, `research_id`, `warnings`, or `research_reports.report`. Diagnostics may return `run_id`, `status`, `error_code`, `created_at`, `started_at`, `finished_at`, and a duration derived from the two timestamps. Usage aggregates the five `GraphUsage` integers. There is no durable cost snapshot on `research_runs`, so `cost_estimate` is null, `coverage` is `unavailable`, and `pricing_version` is null.

The admin UI lives in the Phase 9 `(app)` group. `GET /auth/me` already returns `role`. The header shows Admin only when `role` is `admin`. The shell stays `max-w-2xl`; wide tables scroll inside the column. Extend `isAllowlistedPath` with the exact admin paths and one evaluation-detail UUID pattern so a session expiry can return there. Reject every other `next` value, as ADR-009 C2 requires.

### C6 — Step 1 boundary

Step 1 may add the two models, one Alembic revision, the repository insert/read functions, and their tests. It does not change the evaluation CLI, `baseline.json`, research routes, the proxy, or the Next.js app.

## Consequences

### Positive

- Queryable, reproducible history with immutable cases and strict provenance.
- Security boundaries stay aligned with Phase 8.
- Existing offline CI gate and live judge cost controls are preserved.
- Admin UI can communicate uncertainty instead of overstating research accuracy or provider spending.

### Negative / accepted limitations

- Import remains manual and requires operator DB access.
- Historical artifacts do not prove their original execution timestamp/commit.
- Live judge labels are not independently provider-attested and may reflect a small authored dataset.
- Usage/cost analytics will initially have incomplete dollar coverage.
- Admin cannot inspect user research content, even for troubleshooting, without a separately reviewed privacy policy.
