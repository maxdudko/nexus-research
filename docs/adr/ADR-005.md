# ADR-005 — Request-scoped SSE and Domain-backed Research History

**Status:** Accepted for Phase 5 design  
**Date:** 2026-10-17  
**Context:** Nexus Research Phase 5 — Product UI  
**Related:** ADR-003 (RAG), ADR-004 (LangGraph), Phase 5 `spec.md` and `plan.md`

## Context

Phase 4 provides `POST /api/v1/research/run`: an HTTP request waits for a bounded LangGraph run. PostgreSQL checkpoints save graph state; they do not schedule background work or automatically resume crashed runs. Phase 5 needs a web interface with observable progress, history, PDFs and citations, while preserving the small educational MVP infrastructure.

## Decision 1 — Request-scoped SSE over HTTP POST

Add `POST /api/v1/research/stream` returning `text/event-stream`. The stream request owns the graph execution; no detached background task, Redis queue, Celery, worker or automatic resume. Keep existing `/run` endpoint compatible. The client uses `fetch` with a streaming parser, not native `EventSource`, because it must POST JSON.

**Why:** smallest change to Phase 4 semantics; immediate progress UX; no new infrastructure.  
**Trade-off:** browser disconnect, proxy interruption or server shutdown can stop the research; progress cannot be replayed. Reconnect is **not** resume.

## Decision 2 — PostgreSQL domain tables, separate from checkpoints

Add `research_runs` and `research_reports` through Alembic. Run metadata and structured reports are queryable via stable list/detail endpoints. Checkpoint tables remain an internal LangGraph implementation detail.

**Why:** history, pagination and report retrieval should survive changes in graph state schema and checkpointer implementation.  
**Trade-off:** domain state and checkpoint state can temporarily disagree after failures. Use explicit transition ordering, idempotent finalization and honest stale-running UI; do not pretend to have a distributed transaction.

## Decision 3 — One run ID across layers

Mint `run_id` once before starting the graph, insert domain `running` row, use the same UUID as LangGraph `thread_id`, and include it in all SSE events and history URLs. `research_id` continues to scope evidence and may be reused for PDF-first research. It is **not** an authentication token.

**Why:** simple correlation across frontend, domain history, checkpoint and logs.  
**Trade-off:** a single research scope can contain multiple runs; history and evidence scope must not be conflated.

## Decision 4 — Terminal persistence precedes terminal SSE

After validating final graph state, atomically write terminal `research_runs` status and (on success) `research_reports` JSONB, then emit `research.completed`. Failure/interruption writes safe status/error code before emitting terminal failure when possible. No `completed` event is emitted if domain commit fails.

**Why:** a client that receives completion can immediately GET a durable report.  
**Trade-off:** if connection dies after DB commit but before terminal event, UI sees ambiguous EOF; user can refresh history.

## Decision 5 — Progress derived from allowlisted LangGraph node updates

Translate `astream(stream_mode="updates")` into versioned `research.started`, `research.progress`, and terminal events. Do not expose `ResearchState`, full node updates, evidence passages or model internals. Use heartbeats for liveness, not fabricated progress.

**Why:** stable public protocol and reduced leakage risk.  
**Trade-off:** node-level progress is coarse; per-page indexing progress requires future custom events.

## Decision 6 — Next.js frontend, thin integration

Create `apps/web` with Next.js App Router, TypeScript and Tailwind. Use a typed fetch API client and a robust POST SSE parser. Prefer same-origin API routing to FastAPI. Avoid heavyweight client state management for the MVP.

**Why:** straightforward product UI while keeping AI and business logic Python-first.  
**Trade-off:** adds Node tooling and cross-stack test/build steps.

## Decision 7 — PDF indexing before run; no durable file storage

Reuse `POST /api/v1/evidence/pdf` and stable `research_id`. Uploaded PDF text is indexed in Qdrant and metadata in PostgreSQL. Do **not** store original PDF bytes or claim that a PDF citation can reopen a file after reload. Render source/page reference only unless an independently valid URL exists.

**Why:** reuses Phase 3; avoids introducing S3/local file storage.  
**Trade-off:** no built-in PDF viewer, no durable original-document download, no automatic re-index after vector loss.

## Decision 8 — Single-user demo boundary

No accounts or permissions in Phase 5. History endpoints and evidence scopes are only suitable for a local/trusted single-user environment. Do not deploy them publicly without auth, authorization, rate limiting and resource isolation.

**Why:** matches roadmap MVP boundaries.  
**Trade-off:** not a public multi-tenant SaaS; random UUIDs do not provide sufficient access control.

## Decision 9 — No automatic resume or exactly-once guarantee

Cancellation cleanup is best effort; stale `running` records can remain after crashes. Retries start a **new** run. Provider calls and ingestion can be repeated under failure conditions; reuse Phase 3 idempotency but do not promise exactly-once external side effects.

**Why:** honest lifecycle semantics without a job coordinator.  
**Trade-off:** interrupted runs may incur sunk API cost and require manual retry.

## Alternatives considered

| Alternative | Decision | Reason |
|---|---|---|
| Polling-only with synchronous `/run` | Rejected | No intermediate visibility and difficult request UX |
| WebSockets | Rejected | Unnecessary bidirectional protocol for one-way progress |
| Native `EventSource` GET | Rejected | Cannot send POST JSON body without separate start/job lifecycle |
| Background task in FastAPI | Rejected | Not durable and creates misleading disconnect guarantees |
| Celery/Redis or worker queue | Deferred | Better durability but outside Phase 5 budget |
| Read history from LangGraph checkpoints | Rejected | Couples product API to execution internals |
| Persist reports only in browser | Rejected | Cannot revisit across devices/browser resets; no authoritative history |
| Store PDF files now | Deferred | Adds lifecycle/security/storage work beyond Phase 5 |
| Add user auth now | Deferred | Product remains local/trusted demo; public deployment forbidden |

## Consequences and follow-up

**Positive:** real-time demo UX, persisted history, stable citations, minimal infrastructure.  
**Negative:** no durable execution, no SSE replay, coarse progress, duplicated run/checkpoint persistence, no PDF viewer.  
**Phase 6:** tracing, grounding evaluation, physical provider cost metrics, failure injection and security hardening.  
**Phase 7:** deployment streaming configuration, demo packaging, operational docs.  
**Revisit execution model when:** runs regularly exceed request/proxy limits, users need guaranteed completion after disconnect, or concurrent/public usage becomes a requirement. At that point introduce explicit job lifecycle and durable queue, retaining domain history and public event schema where possible.
